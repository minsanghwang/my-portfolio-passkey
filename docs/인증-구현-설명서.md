# 인증 구현 설명서 — 패스키로 잠근 나만의 자리

- 공개 주소(HTTPS): https://my-portfolio-passkey.vercel.app  (첫 화면 = 공개 소개 페이지, 시크릿 창에서 로그인 없이 열림)
- 소스: https://github.com/minsanghwang/my-portfolio-passkey
- 이 화면과 DB의 비공개 항목은 전부 **데모용으로 만들어 넣은 내용**입니다. 실제 연락처·번호는 없습니다.

## 확인 방법 (4줄)

1. **어디로 가나요** — https://my-portfolio-passkey.vercel.app 을 열고 맨 아래 `06 · 나만의 자리 (PRIVATE)`로 내려갑니다(상단 메뉴 "나만의 자리 🔒").
2. **세 단계 안에 무엇을 하나요** — ① "처음이라면" 칸에 계정 이름(영문 소문자·숫자 3~24자)과 패스키 이름을 적고 ② "패스키 만들고 들어가기"를 누른 뒤 ③ 기기 창에서 지문·PIN 등으로 확인합니다. (이미 만들었다면 "패스키로 들어가기")
3. **무엇이 보이면 통과인가요** — "○○ 님의 자리"와 나만 볼 수 있는 항목 3개, "내 패스키" 목록(이름·등록한 날짜·저장 위치)이 보이고, 로그아웃하면 다시 잠금 화면이 됩니다. 공개 소개 영역은 로그인 없이 그대로 보입니다.
4. **안 될 때는 무엇이 보이나요** — 등록 창을 취소하면 "등록을 취소했습니다. 서버에는 계정도 패스키도 저장되지 않았습니다.", 삭제했거나 등록 안 된 패스키로 들어가면 "서버에 등록되어 있지 않은(또는 삭제된) 패스키입니다.", 마지막 패스키를 지우려 하면 "마지막 패스키는 지울 수 없습니다…"가 나옵니다.

## AI와 내 판단 (3줄)

> ⚠️ 아래는 이 작업 기록을 바탕으로 AI가 쓴 **초안**입니다. 내가 실제로 어떻게 판단했는지에 맞게 직접 고쳐서 제출하세요.

- **AI에게 맡긴 일**: 서버(등록·로그인·로그아웃·비공개 조회·패스키 삭제)와 화면 코드 작성, DB 표·함수 만들기, 배포 설정, 확인용 콘솔 도구 작성.
- **내가 직접 판단한 일**: 새 Supabase 프로젝트를 만들어 쓸지, GitHub 저장소를 직접 만들지, AI가 막힌 일(DB 함수 만들기)을 다시 시도시킬지, 확인을 개발자도구 방식으로 할지, 어떤 확인을 꼭 해야 하는지(두 번째 패스키 등).
- **AI 말을 따르지 않은 일**: 처음에 AI가 코드로 보상하는 방식(계정·패스키 저장 중 실패 시 되돌리기)으로 구현했는데, "DB 함수로 쓰라"고 요구해 DB 함수 방식으로 바꾸게 했습니다.

## ① 무엇으로 붙였나

**라이브러리를 써서 직접 서버를 만들었습니다.** 로그인 서비스(Clerk·Auth0·Supabase Auth 같은 것)에 맡기지 않았습니다.

| 역할 | 쓴 것 |
| --- | --- |
| 패스키 규격 처리(질문 만들기, 등록·서명 확인) | 라이브러리 **SimpleWebAuthn** (`@simplewebauthn/server` v13) |
| 서버 | Supabase Edge Function 한 개 (`passkey-api`). 세션·질문·패스키 관리 로직은 직접 작성 |
| 저장소 | Supabase Postgres (표 5개) |
| 화면 호스팅 | Vercel (정적 페이지 + `/api/*`를 서버 함수로 이어 줌) |
| 브라우저 쪽 | 브라우저 기본 기능 `navigator.credentials.create/get` 을 직접 호출 (`js/auth.js`) |

Supabase는 DB와 함수 실행 환경만 쓰고, Supabase 로그인 기능(Auth)은 쓰지 않았습니다.

## ② 왜 그걸 골랐나

- 과제가 "비밀번호 없이, 서버는 공개키만 갖고, 로그인 때마다 새 질문을 서명" 하는 구조를 직접 보여 달라고 해서, 흐름이 코드에 그대로 보이는 **직접 구현 + 검증 라이브러리** 방식을 골랐습니다. 서명 검증 같은 암호 부분을 직접 짜면 틀리기 쉬워서 그 부분만 검증된 라이브러리에 맡겼습니다.
- 서비스에 통째로 맡기면 질문 보관·재사용 거절·세션이 어디서 일어나는지 설명서 ③·④에 적기 어렵습니다.
- 개인키는 기기 밖으로 나오지 않고 서버에는 공개키만 있어서, DB가 새어도 로그인에 쓸 비밀이 없습니다(세션 토큰도 해시만 저장).
- **세션 방식**: 서버가 세션을 보관하는 방식입니다(JWT 같은 자체 완결 토큰이 아님). 로그인에 성공하면 무작위 32바이트 값을 `__Host-sid` 쿠키(HttpOnly, Secure, SameSite=Strict, 1시간)로 주고, 서버에는 그 **SHA-256 해시만** 저장합니다. 로그아웃하면 서버의 세션 행이 지워져서 같은 쿠키를 다시 보내도 거절됩니다(= 즉시 무효화 가능).
- **패스키가 저장되는 곳**: 내가 등록한 패스키 `aleph`는 **Google 비밀번호 관리자**(동기화되는 패스키)입니다. 근거: 서버가 받은 인증기 식별값(AAGUID)이 구글 비밀번호 관리자 값이고, `multiDevice`·백업됨으로 기록됐습니다. 두 번째 패스키는 실제 기기가 아니라 **Chrome 개발자도구의 가상 인증기**에 만들었습니다(보안 키·휴대폰이 없어서). 화면의 "저장 위치(추정)"는 인증기 식별값·전송 방식으로 **추정한 문구**라서 가상 인증기를 "이 기기 자체"로 표시합니다.

## ③ 어디를 어떻게 고쳤나

1번 과제의 공개 소개 페이지 내용은 그대로 두고, **더하기만** 했습니다.

| 파일 | 한 일 |
| --- | --- |
| `index.html` | 상단 PUBLIC 띠, 메뉴 "나만의 자리 🔒", 공개/비공개 경계선, 잠금 화면과 열린 화면의 뼈대 추가. 비공개 내용은 HTML에 없고 비밀번호 입력칸도 없음 |
| `css/styles.css` | 공개/비공개 구역 표시와 나만의 자리 스타일 추가 |
| `js/auth.js` | 브라우저 쪽 흐름 전체(아래 표) |
| `supabase/functions/passkey-api/index.ts` | 서버 흐름 전체(아래 표) |
| `supabase/migrations/001_init.sql`, `002_functions.sql` | 표(공개키만 저장·비밀번호 칼럼 없음, RLS 켜고 공개 키 권한 회수), 계정 만들기·마지막 패스키 보호 DB 함수 |
| `vercel.json` | `/api/*`를 서버 함수로 이어 주고(같은 출처, 쿠키 유지), 보안 헤더(CSP 등) 설정 |

**네 가지 흐름의 소스 위치**

| 흐름 | 브라우저(`js/auth.js`) | 서버(`index.ts`) |
| --- | --- | --- |
| 등록 | `register()` L168 | `registerOptions` L260 → `registerVerify` L290, 취소 `registerCancel` L340 |
| 로그인 | `login()` L200 | `loginOptions` L349 → `loginVerify` L360 (질문 소진 `consumeChallenge` L183, 세션 발급 `createSession` L206) |
| 로그아웃 | `logout()` L222 | `logout` L399 |
| 비공개 자료 조회 | `renderNotes()` L141 | `requireSession` L223 → `privateNotes` L414 / `privateNotesOfAccount` L419 |
| 패스키 관리 | `addPasskey` L235, `deletePasskey` L267 | `addPasskeyOptions/Verify` L434·L460, `deletePasskey` L501 + DB 함수 `delete_passkey_guarded` |

**다른 계정 접근을 막는 코드 위치**: `index.ts`의 `requireSession`(세션 없으면 401, L223)과 `requireOwner`(주소의 계정이 세션의 계정이 아니면 403, L238). 주소·쿼리·본문에 적은 계정 id는 읽지 않고 항상 **세션의 계정**으로만 조회합니다(`privateNotes` L414). 남의 패스키 id로 삭제를 요청해도 "내 계정 안에서만" 찾으므로 404입니다.

## ④ 안 열리는 것을 확인한 기록

모두 배포된 주소에서 브라우저 개발자도구로 실행했고, 서버 DB와 대조했습니다. 도구는 `test/evidence-console.js`, 원본 출력은 `docs/evidence/확인기록.md`에 있습니다. 시각은 UTC.

### 확인 1. 로그인 없이 비공개 자료 열기

| | 요청 | 결과 |
| --- | --- | --- |
| 성공 | 로그인 후 `GET /api/private/notes` (03:20:45) | **200**, 내 항목 3개 |
| 거절 | 쿠키 없이 `GET /api/private/notes` | **401** `unauthenticated` |
| 거절 | 쿠키 없이 `GET /api/me`, `GET /api/passkeys`, `GET /api/private/accounts/<id>/notes`, `DELETE /api/passkeys/abc` | 전부 **401** |

공개 소스(`/`, `js/auth.js`, `js/main.js`, `css/styles.css`)에서 비공개 항목 문구와 비밀번호 입력칸을 찾았으나 **없음**.

### 확인 2. 다른 계정의 자료 열기 (계정 2개, 양방향)

계정 `sange`(id `3a7b368e-…`)와 `demo-b`(id `4269ce12-…`)는 서로 다른 항목 3개씩을 가집니다.

| 방향 | 성공한 요청 | 거절된 요청 | 전/후 개수 |
| --- | --- | --- | --- |
| demo-b로 로그인 (03:30) | 내 id 경로 → **200**, 3개 | sange id 경로 → **403** `forbidden_other_account` | 3 → 3 |
| sange로 로그인 (03:30) | 내 id 경로 → **200**, 3개 | demo-b id 경로 → **403** `forbidden_other_account` | 3 → 3 |

- `?account=<남의 id>`를 쿼리에 붙인 요청은 **무시**되고 200으로 내 항목(응답 소유자 = 로그인한 계정)만 돌아옴.
- DB 확인: 요청 뒤에도 항목은 sange 3개, demo-b 3개 그대로.

### 확인 3. 이미 쓴 질문(challenge) 다시 보내기

| | 요청 | 결과 |
| --- | --- | --- |
| 성공 | 화면에서 로그인 `POST /api/login/verify` (03:20:45) | **200**, 세션 발급, 질문 `used_at` 기록 |
| 거절 | 같은 요청 본문을 그대로 재전송 | **400** `challenge_already_used` |

- 질문 3번 요청하면 3개 모두 다른 값(서버 DB에 각각 저장, 유효 5분).
- 로그인 요청 본문의 항목: `id, rawId, type, authenticatorAttachment, clientDataJSON, authenticatorData, signature, userHandle` — **개인키·비밀번호 항목 없음**(`ev.bodyCheck()`).

### 확인 4. 패스키를 지운 뒤 로그인

| | 요청 | 결과 |
| --- | --- | --- |
| 성공 | 남은 패스키 `aleph`로 로그인 (03:38:48) | **200**, 세션 발급 |
| 거절 | 방금 지운 패스키 `네번째`의 서명으로 로그인 (03:38:00, 질문은 사용 처리됨) | **401** `passkey_not_registered` |
| 거절 | 남은 마지막 패스키 `aleph` 삭제 시도 | **409** `last_passkey`, DB에 그대로 남음 |

- 패스키 2개(`aleph`, `두번째`)를 이름·날짜·저장 위치와 함께 목록에 표시했습니다. 확인용으로 가상 인증기에 만든 `세번째`를 지운 뒤(03:32) 남은 `aleph`로 로그인이 됐고(03:37), `네번째`를 지운 뒤에도(03:38) `aleph`로 로그인이 됐습니다(03:38:48). `두번째`를 지운 뒤에는 목록에 `aleph`만 남았고(`ev.passkeys()`) 그 뒤에도 `aleph`로 다시 로그인했습니다(아래 세션 재사용 확인용 로그인).
- **남은 패스키가 0개가 되는 경우**: 서버가 마지막 패스키 삭제를 거절해서 0개가 될 수 없습니다. 이 데모에는 계정 복구 수단이 없기 때문입니다(⑥ 참고).

### 추가 확인

| 항목 | 성공 | 거절 |

| 로그아웃 뒤 같은 세션 재사용 (`curl`) | 로그인 중 `GET /api/me` → **200** | 로그아웃 뒤 같은 쿠키로 → **401** (DB 세션 행 0개) |

세션 쿠키 값은 이 문서에 적지 않았고, 서버 DB에는 해시만 있습니다.

## ⑤ AI와 나

- AI(Claude)가 서버·화면·DB·배포 설정 코드와 확인 도구를 작성했고, 확인 요청은 내가 브라우저에서 직접 실행해 결과를 AI에게 보여 주었습니다. 서버 DB 대조는 AI가 했습니다.
- 내가 정한 것: 새 DB 프로젝트 사용, 저장소 직접 생성, 막힌 작업 재시도 지시, 확인 방식 선택, 마지막 패스키 삭제·세션 재사용까지 확인할지 여부.
- AI가 처음에 코드로 보상하는 방식으로 짠 부분을 내가 DB 함수로 바꾸게 했고, 내가 배포 사이트를 AI가 직접 호출해 확인하게 하려 했으나 이 작업 환경의 네트워크 제한으로 불가능해서 사람이 대신 실행하는 방식을 썼습니다. AI는 제한을 우회하지 않았습니다.

## ⑥ 아직 못 막은 것

| 약점 | 설명 |
| --- | --- |
| 계정 복구 수단 없음 | 모든 기기를 잃으면 그 계정에 못 들어옵니다. 그래서 마지막 패스키 삭제는 서버가 막습니다. 이메일 복구·복구 코드는 만들지 않았습니다. |
| 누구나 계정을 만들 수 있음 | 가입에 제한이 없어 한도(50개)까지 계정을 채울 수 있습니다. 한도에 도달하면 새 가입이 막힙니다. |
| 요청 횟수 제한 없음 | 로그인·질문 요청을 계속 보내면 `challenges` 표가 쌓입니다(1시간 지난 것은 요청 때 지워지지만 요청이 없으면 안 지워짐). 로그인 실패 횟수 제한도 없습니다. |
| 세션은 절대 1시간, 회전 없음 | 쿠키가 탈취되면 만료 전까지 쓸 수 있습니다. 로그아웃 때만 즉시 무효화됩니다. |
| 동기화 패스키는 복제 감지가 약함 | 구글 비밀번호 관리자 패스키는 서명 횟수가 0으로 와서 서명 횟수 검사로 복제를 못 잡습니다. |
| 인증기 종류를 검증하지 않음 | 증명(attestation)을 받지 않아서 "어떤 기기인지"를 서버가 믿을 수 없고, "저장 위치"는 추정입니다. 가상 인증기도 기기처럼 보입니다. |
| 서버 키 노출 시 전체 노출 | 서버 함수가 DB 관리 권한 키로 접근하므로 그 키가 새면 DB 전체가 열립니다(Supabase 설정에 보관, 저장소에는 없음). |
| 서버 함수가 공개 주소로 열려 있음 | 함수는 로그인 토큰 없이 호출 가능하게 두었고 접근 제어는 앱의 세션·허용 출처 검사로 합니다. |
